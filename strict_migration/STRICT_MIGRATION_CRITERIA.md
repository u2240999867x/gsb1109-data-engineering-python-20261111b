# 历史 SQLite 特征列迁移 STRICT 表：按实际存储值的分区判据

所有结论均在本仓库 sqlite-utils 源码与 SQLite 3.53 上实测，复现脚本：
`strict_migration/migrate_demo.py`（运行：`.venv/bin/python strict_migration/migrate_demo.py`）。

## 1. 先厘清 sqlite-utils 导入时发生了什么

- CSV/TSV 路径（`rows_from_file`，`sqlite_utils/utils.py:288`）：DictReader 给出的**每个值都是 str**，没有引号与否的区别，`1` 和 `"1"` 落库为同一 TEXT。
- JSON/JSONL 路径（`sqlite_utils/utils.py:338`）：保留 JSON 标量类型；列类型由
  `types_for_column_types()`（`sqlite_utils/utils.py:140`）推断，混合列按
  `{int,bool}→int`、`{int,float,bool}→float`、`{bytes,str}→bytes`、其余→str 塌缩。
- 建表类型来自 `COLUMN_TYPE_MAPPING`（`sqlite_utils/db.py:372`）：`bool→INTEGER`、
  `dict/list/tuple→TEXT`（经 `jsonify_if_needed()` 序列化，`sqlite_utils/db.py:5501`）、
  `Decimal→REAL`、日期/UUID→TEXT；STRICT 建表时 `FLOAT` 被改写为 `REAL`
  （`sqlite_utils/db.py:1640`），且 STRICT 仅在 SQLite ≥ 3.37 可用
  （`supports_strict`，`sqlite_utils/db.py:1154`）。
- 写入由 SQLite 的**列亲和性**决定最终存储类，与 Python 侧类型推断不是一回事。

结论：迁移判据必须建立在成品库的**实际持久值**上，即 `typeof(x)` + `quote(x)`，
而不是建表 DDL 里的声明类型，也不是对原始输入的猜测。

## 2. 三个分区的判据（按持久值 × 目标 STRICT 类型）

脚本用引擎权威探针 `StrictProbe` 分区：把持久值真插进各类型的 STRICT 临时表，
比较插入前后的 `quote()`，不手写转换规则（SQLite 的数值文本判定比正则复杂，
实测 `'01'`/`'+1'`/`' 1 '`/`'1.0'`/`'1e0'` 进 INTEGER 都变成整数 1，而 `'0x1'` 被拒）。

| 分区 | 判定 | 典型持久值 → 目标列 | 实测表现 |
|---|---|---|---|
| **可无损迁移** | 探针接受且 `quote()` 前后完全一致（同存储类、同位序列） | TEXT→TEXT、BLOB→BLOB、integer→INTEGER、有限 real→REAL、NULL→可空列、任意类型→ANY | 字节级不变 |
| **仅数值等价** | 探针接受、`quote()` 变化但数值精确相等 | `'01'/'1.0'/' 1 '`(text)→INTEGER 1；`1`(integer)→REAL 1.0；`1`(integer) 与 `true` 落库同为 integer 1 | 存储类/前导零/空白/布尔语义丢失，数值不变 |
| **无法从现库还原原输入** | 探针拒绝、接受但数值已变、或值已被静默篡改 | `'AB3'`→INTEGER（拒绝）；BLOB→TEXT（拒绝）；`'1.5'`→INTEGER（中间 REAL 非整，拒绝）；`9007199254740993`(integer)→REAL（舍入）；NaN→NULL；inf→`9.0e+999` | 原输入信息在成品库已不存在或被改写 |

两个必须单列的静默篡改（实测）：

- **NaN**：Python `float('nan')` 经 sqlite3 绑定后落库为 `NULL`（`typeof='null'`），
  成品库无法区分“真空值”与“NaN 变来的 NULL”。
- **超大整数**：超过 int64 的整数在**导入阶段**就抛 `OverflowError: Python int too
  large to convert to SQLite INTEGER`，整批失败、旁路后该行不入账（只有台账行数对账
  才能发现“少了一行”）。能入库的 int64 若在迁移时改投 REAL，绝对值超过 2^53 的部分
  必然丢精度（探针按 `abs(v) > 2**53` 直接判不可还原）；但若该列在导入时就已被
  推断为 REAL（混合列），精度丢失发生在入库前，成品库只存着舍入后的浮点，探针会
  判“无损”——这不是误判，而是探针的能力边界：**它只能保证迁移不引入新损坏，
  发现不了入库前的旧损坏**。

## 3. 迁移后的判等规则：主键与关联列必须按它核对

- 普通比较仍走亲和性：非 STRICT 与 STRICT 表之间 `integer 1 = text '1'` 都成立，
  但 `1 IS '1'` 为假；**`=` 比数值，`IS`/`quote()` 比存储身份**。
- STRICT 只允许五种声明类型 `INTEGER/REAL/TEXT/BLOB/ANY`；ANY 列保留写入时的存储类，
  实测 `1`、`'1'`、`1.0`、BLOB、NULL 可同列共存且互不相等，**ANY 可以做主键**，
  是无台账时混合键列唯一能自动无损保身份的选项（代价是放弃类型约束）。
- **STRICT 表不支持 `WITHOUT ROWID`**（实测语法直接报错）；迁移这类表必须改成普通
  rowid 表，物理布局变化，需排查依赖 rowid 的代码。
- `INTEGER PRIMARY KEY` 是 rowid 别名：插入文本 `'1'` 会被强转为整数 1，因此
  `'1'`、`'01'`、`1.0` 在该键上全部撞同一 rowid；复合主键走普通亲和比较，规则相同。
- 实体闸门（脚本 `key_merge_gate`）：对键列每个持久值做探针转换并按**目标键值**分桶，
  一个桶里出现 ≥2 个源行即为实体合并；外键（`fk_join_check`）再用同一判等检查子表
  外键迁移后是否**唯一命中**一个父实体，出现多候选即“歧义”，无候选即“悬空”。
- **单行可转 ≠ 全表可迁**：脚本末段实测 5 行数据每一行单独都能写进 STRICT INTEGER，
  但以该列做主键时 4 行被 `UNIQUE constraint` 拒绝、5 个实体塌成 1 个；换成稳定业务列
  做主键则 5 行全部成功。单元格级分区通过只是必要条件，键级唯一性闸门通过才是充分条件。

## 4. 两批原始输入：同 typeof、同持久值，不同业务编号

### 批次一 CSV（`ledgers/batch_csv/`）——存储类在导入时全部塌成 TEXT

| 业务编号 | 原始 `code` 字面值 | 成品库持久签名 `(typeof, quote)` | 投 INTEGER 的分区 |
|---|---|---|---|
| CSV-001 | `1` | `(text, '1')` | 仅数值等价 |
| CSV-002 | `"1"`（带引号） | `(text, '1')` | 仅数值等价 |
| CSV-003 | `01` | `(text, '01')` | 仅数值等价 |
| CSV-004 | `1.0` | `(text, '1.0')` | 仅数值等价（探针实测可转整数 1） |
| CSV-005 | `AB3` | `(text, 'AB3')` | 无法还原（STRICT 拒绝） |

CSV-001 与 CSV-002 的输入差异（有无引号）在成品库**已经不存在**；前四行业务编号不同，
投 INTEGER 后全部塌成目标键 1，闸门报 1 个合并键；子表外键 O-C1/O-C2/O-C4 迁移后
对父表都是“歧义，候选 3 个”，O-C3（`AB3`）直接悬空。

### 批次二 JSONL（`ledgers/batch_nl/`）——混合标量在导入时按亲和性塌缩

规范路径用 `insert_all` 一次性推断列类型：因为同列出现 int/true/float，
`types_for_column_types()` 把 `code`、`qty` 都建成 REAL，所有标量在**导入阶段**
就被绑定为浮点；超 int64 的行（NL-007）整批会 OverflowError，真实 ETL 旁路后该行不入账。

| 业务编号 | 原始 `code` | 成品库持久签名 | 投 REAL（与现存储一致） | 投 INTEGER |
|---|---|---|---|---|
| NL-001 | `1`（int） | `(real, 1.0)` | 无损 | 仅数值等价 |
| NL-002 | `true`（bool） | `(real, 1.0)` | 无损* | 仅数值等价 |
| NL-003 | `1.0`（float） | `(real, 1.0)` | 无损* | 仅数值等价 |
| NL-004 | `null` | `(null, NULL)` | 无损（可空列） | 无损 |
| NL-005 | `9007199254740993` | `(real, 9007199254740992.0)` | 探针判无损** | 仅数值等价（且已是错值） |
| NL-006 | `2`，`qty: NaN` | code `(real, 2.0)`；qty 落 `(null, NULL)` | — | — |
| NL-007 | `100000000000000000000` | **导入即 OverflowError，整行被旁路，库中不存在** | 成品库不可见 | 同左 |

\* “无损”仅指与成品库持久值字节一致；`true`/`1`/`1.0` 的输入类型身份在导入时
已全部塌成 `real 1.0`，三个业务编号 NL-001/002/003 共享同一持久签名，投任何
数值型主键都会合并为一个实体。

\*\* 这是探针边界的关键教学点：NL-005 投 REAL 被判“可无损迁移”，是因为**损坏发生在
导入阶段**（台账的 9007199254740993 已被 REAL 舍入成 9007199254740992.0），
迁移探针只能对成品库负责、无法发现入库前的精度丢失。只有拿台账逐值对账才能抓到
这类差异；只有成品库时，这个错误值会被当作合法数据一路带进 STRICT。

## 5. 两种信息条件下各自能承诺什么

### 有原始输入台账（原始 CSV/JSONL + 导入规则可重放）

- **可承诺自动无损迁移**：在重放库上跑探针，所有单元格进 LOSSLESS 桶、且键级闸门无合并
  的表，可直接自动迁移；CSV 的文本特征列选 TEXT、JSONL 同构数值列选对应数值类型即属此类。
  迁移前再用台账与成品库做逐值对账，把“入库前旧损坏”（如 NL-005 的 REAL 舍入）与
  迁移本身分开报告。
- **可自动转换但须业务签收“仅数值等价”**：前导零、引号、空白、`1.0`/`1e0`、bool/int
  等，台账保留了原字面值，转换可回溯、可生成差异清单，自动迁移 + 人工签收表示丢失。
- **不可自动、但可定位可补登**：NaN、溢出整数（NL-007 在导入异常/旁路清单里）、非数值文本、
  超 2^53 精度丢失——原输入仍在台账，能逐行找回并人工裁定（改类型/修正/拒绝），
  不会出现“悄无声息少一行”。
- **键合并可消解**：用台账里的稳定业务编号（如 `biz_id`）重建实体身份，重新分配代理键、
  按业务编号而非塌缩后的 code 重写外键；合并冲突可自动检测、人工裁决后再自动执行。

### 只有成品库（无任何原始输入）

- **可承诺自动无损迁移**：仅限探针全列 LOSSLESS 且键级唯一性闸门通过的表——
  纯 TEXT→TEXT、纯 BLOB→BLOB、纯同构 integer→INTEGER、有限 real→REAL；
  混合存储类的列想自动无损只能整体选 **ANY**（保存储类、可做主键，但是多态列，类型约束落空）。
  注意这里的“无损”只承诺**迁移过程不引入新损坏**，不保证成品库值等于历史真实输入。
- **可自动做“仅数值等价”转换**：NUMERIC 桶可机械搬移，但承诺书中必须写明不保证还原输入
  表示，且不保证区分 bool 与 int（成品库只有塌缩后的同一个值）。
- **不能承诺、必须人工拦截**：
  - 任一 UNRECOVERABLE 单元格（非数值文本、跨存储类、NaN→NULL、inf→9e999、迁移期大整数舍入）；
  - 所有 NULL 无法声明它原本是不是 NaN；
  - **入库前的旧损坏无法识别**：NL-005 那样在导入时已被舍入的值，探针只会判 LOSSLESS，
    错误值会被当作合法数据一路带进 STRICT，无台账则永远无法发现；
  - 键闸门出现合并时，成品库无法判断被吞并的几个持久值对应几个真实实体、谁是谁，
    只能停迁交人工，禁止用“先插进去再说”的方式让 UNIQUE 约束静默丢行；
  - 导入期被拒/旁路的行（如 NL-007）在库里根本不存在，无外部行数台账时**连缺失都无法发现**；
  - 外键出现歧义命中或悬空，只能报障，无法自动消解。

## 6. 建议的落地流程

1. 对每张表声明目标 STRICT 类型，用 `StrictProbe` 按 `typeof+quote` 出三分区计数与样例。
2. 键列（主键、唯一键、外键两端）额外跑 `key_merge_gate` 与 `fk_join_check`，
   输出合并键、歧义/悬空外键清单；任一未清零则该表不得自动迁移。
3. LOSSLESS + 闸门通过 → 自动迁移并做行数、`quote()` 全量比对校验。
4. NUMERIC → 生成差异清单走业务签收；UNRECOVERABLE → 隔离到待查表，有台账回台账补登，
   无台账则保留原表或改 ANY 并挂人工工单。
5. 原 `WITHOUT ROWID` 表改为普通 STRICT rowid 表，回归依赖 rowid 的查询。
